# Сервер VUMEXCLUSIVE CRM

Актуальная схема развёртывания CRM и Telegram-бота на 5 августа 2026 года.

## Текущее состояние

5 августа 2026 года выполнено финальное переключение на собственный сервер:

1. **Основной рабочий контур** — собственный сервер + локальный PostgreSQL.
2. **Старый контур** — Vercel перенаправляет все запросы на новый HTTPS-адрес,
   Supabase сохранён как замороженная резервная копия на момент перехода.
3. **Telegram-бот** — работает на новом сервере в режиме polling. Старый webhook удалён,
   очередь событий при переключении не очищалась.

Новый сервер:

- адрес сервера: `root@45.12.238.157`, Ubuntu 24.04;
- временный HTTPS-адрес: `https://vumexclusive.45-12-238-157.sslip.io`;
- приложение работает от отдельного пользователя `natalivm`;
- код хранится в `/srv/natalivm/releases/<версия>`;
- `/srv/natalivm/current` указывает на активную версию;
- Next.js слушает только `127.0.0.1:3000`, наружу его публикует nginx;
- PostgreSQL 17 слушает только `127.0.0.1:5432`;
- Telegram-бот работает отдельной службой `natalivm-bot.service`.

Финальная синхронизация перенесла из Supabase 19 таблиц и 694 записи. Содержимое каждой
таблицы и последовательности ID были сверены до активации. После переключения серверный
бот обработал ещё 8 новых Telegram-событий; проверка подтвердила, что в новой базе есть
все исходные события и нет дубликатов.

5 августа сервер повторно проверен после установки системных обновлений и перезагрузки:
CRM, PostgreSQL, nginx, firewall, fail2ban, ежедневный бэкап и обновление HTTPS-сертификата
запустились автоматически. Все основные разделы CRM и страницы отдельных клиентов,
занятий и абонементов вернули успешный ответ; ошибок приложения, PostgreSQL и nginx `5xx`
не обнаружено. Свежий PostgreSQL-архив полностью восстановлен в тестовую базу.

## Источник данных после переключения

Единственный рабочий источник данных — локальный PostgreSQL на новом сервере. Повторно
запускать импорт из Supabase после начала работы нельзя: он может заменить более свежие
серверные данные снимком старого контура. Supabase используется только как резервная копия
состояния на момент перехода и автоматически с новой базой не синхронизируется.

## Секреты и доступ

Секретов в GitHub нет. Канонические файлы на сервере:

- `/etc/natalivm/database.env` — подключение новой CRM к локальному PostgreSQL;
- `/etc/natalivm/supabase.env` — подключение к старой Supabase только для копирования;
- `/etc/natalivm/app.env` — пароль CRM и ключ подписи сессии;
- `/etc/natalivm/bot.env` — токен и настройки Telegram-бота.

Каталог доступен только `root` и группе `natalivm`; файлы имеют права `640`.
В активном релизе `.env`, `.env.local` и `.env.bot.local` являются ссылками на эти файлы.

Приватный SSH-ключ хранится только локально в исключённой из GitHub папке
`ДОСТУП-К-СЕРВЕРУ`. Пароль новой CRM сохранён там же в отдельном локальном файле.

## Службы

```bash
systemctl status natalivm-crm
systemctl status natalivm-bot
systemctl status natalivm-backup.timer
```

- `natalivm-crm.service` — новая CRM, включена и работает;
- `natalivm-bot.service` — серверный Telegram-бот, включён и работает;
- `natalivm-backup.timer` — ежедневный бэкап в 03:20 по Москве, включён.

Логи:

```bash
journalctl -u natalivm-crm -n 100 --no-pager
journalctl -u natalivm-bot -n 100 --no-pager
journalctl -u natalivm-backup -n 100 --no-pager
```

## Защита PostgreSQL

- База не доступна из интернета.
- У PostgreSQL включены `data_checksums`, `fsync`, `full_page_writes` и
  `synchronous_commit`.
- Приложение подключается ограниченной ролью `natalivm_app`, а не администратором базы.
- Для зависших запросов настроены тайм-ауты.
- SSH работает по ключу; вход `root` по паролю выключен.
- Firewall пропускает только SSH, HTTP и HTTPS.

## Резервные копии

Ежедневная служба создаёт две независимые копии:

- JSON-снимок приложения: `/srv/natalivm/backups/database`;
- полный архив PostgreSQL: `/var/backups/natalivm/postgres`.

Архивы, полученные при переносе из Supabase, лежат отдельно:
`/var/backups/natalivm/migrations`.

Для каждой копии создаётся SHA-256. PostgreSQL-архив после создания автоматически
восстанавливается в отдельную временную базу; затем сравнивается количество строк во всех
19 таблицах. Только успешное восстановление считается успешным бэкапом. Копии хранятся
35 дней. Веб-приложение не имеет прав менять каталоги бэкапов.

Ручная проверка:

```bash
systemctl start natalivm-backup.service
systemctl status natalivm-backup.service --no-pager
```

## Обновление кода

1. Проверить сборку и отправить код в GitHub.
2. Создать новый каталог `/srv/natalivm/releases/<версия>`.
3. Установить зависимости и выполнить `npm run build` в новом каталоге.
4. Подключить три серверных env-файла символьными ссылками.
5. Проверить новый релиз до переключения.
6. Атомарно изменить `/srv/natalivm/current` и перезапустить только CRM.
7. Проверить вход, клиентов, занятия, финансы и раздел бота.

Старый каталог релиза не перезаписывается и остаётся для отката кода.

## Исторический сценарий синхронизации из Supabase

Сценарий:

```bash
/srv/natalivm/current/deploy/sync-supabase-to-local.sh --activate
```

Он создаёт новый дамп Supabase, восстанавливает его в отдельную базу, сверяет содержимое
19 таблиц и последовательности ID. Этот сценарий уже был выполнен при финальном переходе.
Повторный запуск с `--activate` в рабочей системе запрещён без отдельного плана объединения
данных и свежего резервного архива.

## Telegram-бот после переключения

Бот работает через `natalivm-bot.service` в режиме polling. Webhook не установлен, поэтому
двойной обработки сообщений нет. При запуске служба по умолчанию сохраняет накопившуюся
очередь; `TELEGRAM_DROP_PENDING_UPDATES=1` разрешено использовать только для отдельного
тестового бота.

Для полного сценария записи в разделе CRM «Бот» должны быть заполнены реквизиты оплаты,
адрес офлайн-занятий и ссылка на онлайн-занятие. Эти значения являются рабочим контентом,
а не серверными секретами, и читаются ботом из базы без пересборки приложения.

## Откат

- **Код:** остановить CRM, вернуть `/srv/natalivm/current` на предыдущий релиз и запустить CRM.
- **Последняя синхронизация:** до импорта прежняя локальная база переименовывается и остаётся
  на сервере.
- **Повреждение данных:** восстановить выбранный PostgreSQL-архив сначала в отдельную базу,
  проверить количество строк и только затем переключать приложение.

Откат кода не откатывает данные автоматически.

## Старый контур

- Старый Vercel оставлен только как перенаправление на новый адрес.
- Старый Telegram webhook отключён и не должен включаться повторно.
- Supabase оставлен как замороженный резерв на момент перехода; рабочая CRM туда не пишет.
- Удалять старый контур следует только после согласованного срока хранения резерва.
