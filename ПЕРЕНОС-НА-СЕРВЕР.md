# Сервер VUMEXCLUSIVE CRM

Актуальная схема развёртывания CRM и Telegram-бота.

## Контур

- Сервер: `root@45.12.238.157`, Ubuntu 24.04.
- Приложение работает от отдельного пользователя `natalivm`.
- Код: `/srv/natalivm/releases/<версия>`.
- Активная версия: символьная ссылка `/srv/natalivm/current`.
- Веб-приложение: Next.js на `127.0.0.1:3000`, наружу через nginx.
- База: управляемый PostgreSQL в Supabase. На сервер передаётся только защищённый `DATABASE_URL`.
- Telegram-бот: отдельная systemd-служба, запускается только при окончательном переключении со старого webhook.

Supabase не переносится в локальный PostgreSQL одновременно с веб-приложением. Такой перенос требует отдельного окна без записи или репликации, иначе два экземпляра базы разойдутся.

## Секреты

В GitHub секретов нет. На сервере в активном релизе находятся файлы с правами `600`:

- `.env` — `DATABASE_URL`;
- `.env.local` — `APP_PASSWORD`, `AUTH_SECRET`;
- `.env.bot.local` — `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_IDS`.

Приватный SSH-ключ на сервер не копируется. Он хранится только локально в исключённой из GitHub папке `ДОСТУП-К-СЕРВЕРУ`.

## Службы

```bash
systemctl status natalivm-crm
systemctl status natalivm-bot
systemctl status natalivm-backup.timer
```

- `natalivm-crm.service` — CRM, включена в автозапуск.
- `natalivm-bot.service` — Telegram-бот. До переключения должна быть выключена.
- `natalivm-backup.timer` — ежедневный бэкап Supabase в 03:20 по Москве.

Логи:

```bash
journalctl -u natalivm-crm -n 100 --no-pager
journalctl -u natalivm-bot -n 100 --no-pager
journalctl -u natalivm-backup -n 100 --no-pager
```

## Защита данных и релизов

- Каждый релиз распаковывается в новый каталог, старые файлы не перезаписываются.
- Переключение версии выполняется атомарно через `/srv/natalivm/current`.
- Предыдущий релиз остаётся на сервере для быстрого отката.
- Перед переключением создаётся резервная копия базы.
- Бэкап записывается сначала во временный файл и только после завершения переименовывается.
- Для каждого бэкапа создаётся SHA-256 контрольная сумма.
- После создания автоматически проверяются 19 таблиц, количество строк, уникальность ID и основные связи.
- Серверные ежедневные копии хранятся 35 дней в `/srv/natalivm/backups/database`.
- Каталог бэкапов принадлежит `root`, веб-приложение не может удалять или менять копии.

Ручной бэкап и проверка:

```bash
systemctl start natalivm-backup.service
systemctl status natalivm-backup.service --no-pager
```

## Обновление

1. Проверить и отправить код в GitHub.
2. Сделать локальный и серверный бэкап базы.
3. Загрузить код в новый каталог `/srv/natalivm/releases/<версия>`.
4. Установить зависимости и выполнить `npm run build` внутри нового каталога.
5. Проверить новый релиз до переключения.
6. Переключить `/srv/natalivm/current` и перезапустить только `natalivm-crm`.
7. Проверить вход, клиентов, занятия, финансы и настройки бота.

## Переключение Telegram-бота

До финальной проверки бот продолжает получать события через старый Vercel webhook. Новый серверный процесс не запускается, поэтому двойной обработки сообщений нет.

При окончательном переключении:

```bash
systemctl enable --now natalivm-bot
```

Команда запуска бота удалит старый webhook и включит polling. После этого проверяются `/start`, запись, отправка чека, подтверждение администратором и напоминания.

## Откат

1. Остановить CRM.
2. Перенаправить `/srv/natalivm/current` на предыдущий каталог релиза.
3. Запустить CRM и проверить `/login`.

Откат кода не откатывает данные. Восстановление базы выполняется отдельно и только после проверки нужного бэкапа.

## Что нельзя отключать заранее

- проект Vercel;
- старый Telegram webhook;
- Supabase;
- текущий адрес, которым пользуется преподаватель.

Они отключаются только после проверки нового адреса CRM и работы бота на сервере.
